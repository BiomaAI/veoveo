# Native Audit Measurements, 2026-09-30

The paired workload compares `21711f55` with the unified audit implementation using
queued-record batching. The baseline carries the same request timers and HTTP-to-MCP
observation propagation; its authorization, audit writes and Store behavior are unchanged.
Each gateway uses a matching hosted fixture because the signed request context is a
coordinated hard cut. Both fixtures serve the same catalog and resource payloads.

## Method

The host has a Ryzen 9 5950X with 32 logical CPUs and Linux 6.8. Both gateways use Rust
1.98.1 development builds with debug information and the same external dependency pins.
Each run starts fresh SurrealDB 3.3.0 RocksDB state and two loopback hosted fixtures.
The reference cluster, other test fixtures and Cargo builds are stopped during sampling.
These numbers describe native development execution; they establish no installed,
release-profile or hardware-GPU latency claim.

The official MCP Python SDK 2.0.0 uses `cache=None` so every measured operation reaches
the gateway. One authenticated operator calls `resources/list` and reads
`media://scenarios`. Each method has 20 warm-up calls, 100 sequential samples, then
128 samples in sixteen groups of eight concurrent calls. Each variant has 456 measured
requests. Every operation succeeds and returns a nonempty result.

The response's `x-request-id` joins each sample to gateway timing output. Audit time
includes writer queueing and commit acknowledgement. Request time ends when middleware
receives the response; it excludes client transport time. Policy and upstream stages use
the same observation in MCP dispatch tasks. The [raw samples](native-2026-09-30.csv)
contain milliseconds; p95 is the nearest-rank percentile within each group.

## Results

| Workload | Before total p50 | After total p50 | Before total p95 | After total p95 | Before audit p50 | After audit p50 |
|---|---:|---:|---:|---:|---:|---:|
| Catalog, sequential | 12.72 | 16.17 | 16.83 | 19.14 | 3.23 | 3.40 |
| Read, sequential | 54.63 | 47.33 | 63.89 | 71.92 | 8.41 | 3.22 |
| Catalog, eight concurrent | 26.31 | 24.67 | 59.27 | 60.51 | 7.59 | 7.50 |
| Read, eight concurrent | 82.84 | 67.12 | 109.88 | 109.08 | 22.44 | 11.48 |

Warm catalog samples evaluate no policy in either variant. In the current writer,
audit wait is about 21% of sequential catalog median latency and 7% of sequential
read median latency. At concurrency eight, those ratios are about 30% and 17%.
Read upstream time has a median of 30.78 ms sequentially and 35.87 ms concurrently,
which exceeds the corresponding audit wait. The current request writer commits 497 records,
including warm-up and token issuance, without a failed required commit.

Sequential catalog total latency remains 3.44 ms above the baseline median while
its audit wait differs by 0.17 ms. The difference is outside the measured audit stage;
these measurements do not identify its cause. Read p95 also increases despite a lower
median. A single-host development run does not establish a general throughput claim.

An earlier writer with a fixed five-millisecond gathering window had a 21.19 ms
sequential catalog median and 9.17 ms audit wait. Removing that timer reduces the
current values to 16.17 ms and 3.40 ms while preserving transaction acknowledgement.
The writer still groups records queued by concurrent requests and during the previous
commit. Native replica checks verify that each acknowledged required record is already
readable on another connection and that shutdown seals every accepted record.
