# Media MCP Server

Media discovers provider models, submits generation Tasks, receives signed completion
webhooks, and publishes generated bytes through the Artifact plane.

## Standards And Protocols

| Boundary | Supported profile |
|---|---|
| Model Context Protocol | `2026-07-28` Discover, stateless Streamable HTTP, official Tasks and request-scoped subscriptions under the [hosted contract](../../mcp/contract/DESIGN.md) |
| JSON Schema | 2020-12 input and output contracts; open provider model input schemas |
| MCP Apps | SEP-1865 / `io.modelcontextprotocol/ui` `2026-01-26`; Studio at `ui://media/studio.html` |
| Resource URIs | Veoveo `media://` scheme; prediction and usage builders use the [foundational URI profile](../../platform/types/DESIGN.md) |
| Media catalog cursors | Base64url without padding over JSON `{version:1,collection,after}`; separate usage and prediction collections |
| Generation result | Veoveo `veoveo.ai/media-generation/v1` JSON resource; the Media reader also accepts the retained, unversioned generation Task profile described below |
| Task identity | Native UUIDv7 with the RFC variant, represented as lowercase hyphenated text in usage addresses |
| SurrealDB | Qualified Store driver and query profile `3.2.4`; internal record references, bound parameters, LIVE and change-feed recovery |
| Provider completion | Authenticated signed webhook payloads through the provider adapter; billing uses the adapter's existing reconciliation path |

## Ownership And Packaging

`veoveo-media-mcp` exposes `contract` with default features disabled. This feature owns
prediction identity, generation result DTOs, typed usage and prediction addresses,
cursors and checked pages. It excludes the database driver, HTTP client, MCP integration
and async runtime. Conformance utilities and smoke consumers import these public types
from Media. MCP core has no dependency on the Media library.

`runtime` owns provider access, Artifact publication, Store operations and `MediaReads`.
`mcp` adds the hosted server and protocol adapter. The default feature selects `mcp`.
Provider model DTOs and broader request types still live in runtime modules; their
contract extraction, closed scope vocabulary and checked MCP setup are tracked in the
[foundations plan](../../docs/PLATFORM_FOUNDATIONS_PLAN.md#modular-types-and-server-contracts).

`MediaPredictionId` admits nonempty provider identities up to 512 UTF-8 bytes, excluding
controls and the dot path segments. `MediaPredictionUri` encodes that identity as one
segment, including embedded slashes or reserved characters. Parsing rejects aliases,
extra segments and unsupported queries. Cursors carry the specific collection's ID
type. Entry construction derives repeated IDs from addresses, while decoding checks
ID/address agreement, strict ordering, page size and continuation position.

`MediaGenerationUri` takes a `MediaPredictionId` and addresses the `result` child of
that prediction. `MediaGenerationResult` checks the Task, prediction, result URI and
output count together. Every output carries `MediaOutputArtifactMetadata` with typed
Task and prediction IDs. The builder checks model agreement, output order, distinct
Artifact occurrence IDs and Media presentation URIs. Results contain no download URLs.

## Resource Selection

Discovery declares fixed roots and templates without database enumeration. The
`media://predictions` catalog carries prediction links; `media://usage` carries task
usage links. Both return `{items,limit:100,next_cursor}` with a null terminal cursor.
The `{?cursor}` templates address continuation pages. SQL requests one lookahead row
and returns at most 100 entries to the consumer. Pages represent current reads and do
not promise a snapshot across requests.

`MediaReads` owns public selection over the shared Store connection. SQL applies the
caller tenant, principal, profile and label clearance before grouping, ordering or
limits. Each row must agree with its linked Task's tenant and Media server. The stored
owner envelope must match the indexed owner and profile, including the distinction
between an omitted tenant and an explicit `installation` tenant. Media applies Task
owner policy; a shared Work Context alone grants no additional access.

Prediction selection requires the indexed provider ID to match the stored payload ID.
Usage may precede provider submission; a present provider-job link must match the Task,
tenant, provider and payload identity. Exact reads apply these predicates in the same
statement as record selection. Missing and denied resources have the same public
not-found response. Rust decodes selected rows and validates their types without
post-filtering visibility. Prediction summaries omit provider output URLs.

`media://prediction/{id}/result` reads a completed generation's metadata from the
linked successful Task. SQL applies current owner policy, provider/payload identity,
Task success, the error flag and the result's prediction parent before its one-row
limit. The decoder checks the selected result's profile and internal relationships.
There is no additional result table or copy. This immutable leaf is discoverable by
template and does not accept subscriptions. The prediction resource continues to
provide the provider summary.

Result availability follows Task retention, whose configured default is 30 days;
retention pins can extend it. Artifact metadata and bytes follow their own policies.
A retained result describes the completed output and does not promise that its
Artifact bytes are still available. Artifact access rechecks the Artifact plane's
current policy when a consumer follows an output link.

Queries interpolate only code-owned clause alternatives. Caller values enter as bound
parameters at the driver boundary. The SQL continuation includes an explicit inequality
against the anchor for the qualified 3.2.4 compound-index range behavior; the database
upgrade must requalify that case.

## Subscriptions And Billing

Prediction subscription admission uses the same SQL selection as an exact read. Usage
admission checks the current Task owner and can precede the first ledger row. Index
and cursor-page subscriptions require authentication; subsequent reads reapply caller
authority. Task, provider-job and usage changes invalidate accepted contents through
Store LIVE observations and change-feed recovery. Reconnection also invalidates
accepted resources. Data changes do not announce discovery-list changes.

Internal billing recovery selects terminal provider payloads without matching actual
usage in SQL, checks linked Task/tenant/provider agreement, and walks 100-job pages by
native Store job ID. Billing checks bind both the typed Task and prediction IDs.
Settlement in a different tenant cannot suppress a job with the same provider ID.
Ledger writes reject mismatched Task or provider identities before recording usage.

The signed webhook and existing pending-event/billing reconciliation mechanisms keep
their current completion semantics. Finite recovery budgets and the replacement of
outbox delivery remain work in the foundations plan. Cancellation cannot turn a late
webhook into a successful Task result or permit Artifact capability redemption.

## Catalog Upgrade And Recovery

Media owns the transition from the unbounded usage array and dynamic discovery rows
to the page contract above. This is a coordinated installation upgrade. Drain Media
traffic and subscriptions, stop old replicas, then replace every replica and deploy
consumers that understand pages. Consumers find instance links in the catalogs.
Mixed old/new replicas are unsupported; there is no silent array adapter. The prior
profile is supported only until that installation's scheduled coordinated upgrade.

Before rollout, export the affected Store records and preserve the matching binary
and configuration revisions. Preflight retained Task IDs, provider IDs, owner envelopes
and Task/provider links against the typed profile. Resolve inconsistencies through
operator review; the server does not rewrite or delete rejected records. Valid IDs,
generation schemas and per-task usage reports preserve their existing wire form.
The extraction introduces no persistent data conversion. A rollback drains traffic
again and restores the matching binaries and consumers; retained records stay intact.
Record backup verification and rollback rehearsal in installed acceptance before
removing support for the prior profile.

## Generation Result Profiles And Recovery

Media owns two stored Task result profiles. The unversioned v0 structured content has
`prediction` and `artifacts`; `veoveo.ai/media-generation/v1` also carries its schema
marker, typed Task identity and canonical `result_uri`. Resource reads expose v1.
The private v0 adapter validates retained Artifact attribution and builds the same
checked v1 value. An unknown schema or incomplete v1 is rejected, without falling
through to v0. Reading either profile leaves the persisted Task unchanged.

The current Task producer emits v0. Its output schema and completion links retain
that profile while the resource reader establishes a rollback checkpoint that can
read both versions. The single-result completion handoff is still pending C02 work.
Deploy the reader checkpoint before a v1 producer; drain Media traffic, active Tasks
and subscriptions for that producer transition and replace all replicas and consumers
together. Mixed producer versions are unsupported. A rollback targets the qualified
reader checkpoint and matching consumers, which can still read retained v1 results.

Export affected Tasks and provider jobs before the transition. Preflight both result
profiles, Task/provider relationships and ordered output attribution; keep rejected
records for operator review. No destructive conversion is required. Retire the v0
reader only when every retained or pinned v0 result has expired or passed an
owner-approved migration with backup and reverse-conversion qualification. Installed
transition and rollback rehearsal remain acceptance requirements.

## Qualification And Remaining Work

Native Store tests use separate write and read clients against isolated pinned database
containers. They cover denied rows before page limits, current clearance, optional
tenants, provider-ID collisions, inconsistent links, billing continuation and
subscription admission before usage exists. Webhook integration covers duplicate
receipts, another replica, restart recovery, failure and late completion after
cancellation. Every case has a deadline and owns fixture cleanup.

Contract tests preserve the generation schemas, exercise reserved URI characters,
and reject invalid cursor/page relationships. They also run in an independently
resolved consumer with only the contract feature. Studio pagination has headless
behavioral tests; installed and headed hardware acceptance are separate requirements.
The native MCP smoke exercises generation, typed catalog reads and caller isolation.
Result cases exercise both retained profiles, current clearance, denied malformed
payloads, missing parents and unsuccessful Tasks through separate Store connections.
The MCP smoke reads the complete result and checks it against Task output metadata.

Installed catalog transition and rollback acceptance are pending. Model-catalog paging,
remaining URI builders, provider DTO typing and C02's single canonical result handoff
are tracked in the foundations plan and the [server manual](AGENTS.md).
